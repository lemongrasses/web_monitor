# AIO 系統紀錄器:電腦的黑盒子

[English version](SYSMON.md)

電腦卡住、變得很慢、或是斷電時,證據通常會跟著消失:核心的日誌存在記憶體裡,系統日誌也只記錄各程式印出來的東西。系統紀錄器(`aio-sysmon`)會持續保留一份很小、**斷電也留得住**的機器狀態紀錄,事後就能回答:*出事前幾分鐘發生了什麼?它為什麼停了?*

它獨立於儀表板(儀表板當掉它仍會繼續記錄),只使用 Python 標準函式庫,而且有固定的磁碟預算,所以不會變成問題的一部分。

## 1. 記錄什麼、什麼時候記

細節只在有用的時候才花。

| 層級 | 內容 | 頻率 | 磁碟用量 |
|------|------|------|----------|
| **環狀檔** | 每秒一筆輕量紀錄:CPU 忙碌與等待磁碟的比例、負載、剩餘記憶體、swap、最高溫度、卡在磁碟等待的工作數、紀錄器自己醒來晚了多久(延遲)、上一次寫入磁碟花的時間、磁碟忙碌率、輸入電壓、剩餘磁碟空間 | 每 1 秒記錄,每 5 秒寫入磁碟 | **固定 4 MB**(約 2 小時,寫滿會覆蓋最舊的) |
| **樣本** | 完整樣本:每個核心的 CPU、記憶體細項、swap 活動、磁碟吞吐量與請求時間、每個網路介面、所有溫度、電源軌(電壓與電流)、CPU/GPU 頻率與負載;每分鐘附上耗用資源最多的程序 | 每 5 秒(觸發後的一分鐘內每 1 秒) | 一天約 15 MB,**壓縮後約 2 MB** |
| **事件** | 異常、核心警告與錯誤(記憶體不足、磁碟逾時、熱降頻、GPU 錯誤、卡住的工作)、啟動與停止、時鐘跳變、紀錄器自己的中斷 | 發生時 | 一天幾 KB |
| **快照** | 異常當下的完整狀態:前 2 分鐘逐秒的資料、CPU 與記憶體前 12 名程序、卡在磁碟等待的工作(含核心堆疊)、所有溫度與電源軌、最後 40 行核心訊息 | 只在觸發時;一天最多 120 份,每份 5–25 KB | 有上限(見第 2 節) |

**什麼會觸發詳細紀錄。** 門檻是**依這台機器推算**的,不是寫死的數字,而且狀況要持續幾筆才算,單次雜訊會被忽略:

| 觸發 | 規則 | 這台機器的值 | 推算依據 |
|------|------|--------------|----------|
| `load` | 負載超過門檻持續 10 秒 | 12 | 核心數(8)的 1.5 倍 |
| `cpu_saturated` | CPU 忙碌超過 92% 持續 30 秒 | 92% | |
| `iowait` | 超過 25% 的 CPU 時間在等磁碟,持續 3 秒 | 25% | |
| `memory_low` | 可用記憶體低於門檻 | 1252 MB | RAM 的 8%,至少 512 MB |
| `swap_high` | swap 使用超過 25% | 25% | 僅在機器有 swap 時 |
| `swapping` | 每秒換出超過 2000 頁 | 2000 | |
| `hot` | 最高溫度超過門檻 | 85 °C | 比第一個高溫門檻(95 °C)低 10 °C |
| `disk_wait_tasks` | 4 個以上工作卡在磁碟等待,持續 3 秒 | 4 | |
| `stall` | 紀錄器的 100 ms 睡眠晚醒超過 800 ms | 800 ms | 直接量測延遲 |
| `slow_disk_write` | 寫入並同步一筆樣本花超過 1 秒 | 1000 ms | |
| `disk_space` | 剩餘磁碟空間低於門檻(每小時一次) | 6850 MB | 磁碟的 5%,至少 2 GB |
| `power_dip` | 輸入電壓比自己 10 分鐘的中位數低 12% | 相對值 | 任何供電電壓都適用 |

觸發之後,同一種觸發會安靜 2 分鐘,所以長時間的問題只會留下幾份快照,不會有幾千份。`stall` 是判斷「電腦很卡」最值得看的一項:它代表機器連一個很小的計時器都沒辦法準時執行。

## 2. 容量:它會限制自己

在這台機器(Jetson Orin NX、8 核心、15 GB RAM、134 GB 磁碟)上的實測:

| | |
|---|---|
| 紀錄器的 CPU | 約 **0.9% 單核心**(約佔整台機器的 0.1%) |
| 記憶體 | 約 15 MB(服務被限制在 96 MB 和 15% 單核心以內) |
| 平常一天 | 樣本約 15 MB,壓縮後約 2 MB |
| 保留 30 天的穩定狀態 | 約 **85 MB**:當天的檔案、29 天壓縮檔、4 MB 環狀檔 |
| 全部的硬上限 | **250 MB**(磁碟的 0.3%,介於 60 到 250 MB;較小的磁碟會得到較小的上限) |
| 磁碟寫入量 | 快閃記憶體層級一天約 250 MB,對 NVMe 來說可以忽略 |

達到上限時,最先被捨棄的順序:舊快照(最多佔上限的 40%)、最舊的每日樣本、最舊的事件。超過 30 天的檔案會刪除,前一天的樣本會壓縮(約 7 倍)。

**磁碟保護。** 紀錄器會監看剩餘空間,在磁碟寫滿**之前**就降級:

| 剩餘空間 | 行為 |
|----------|------|
| 高於磁碟的 3%(這裡是 4.1 GB) | 全部功能 |
| 低於此值 | 不寫快照、不做詳細取樣;環狀檔、樣本和事件繼續 |
| 低於 512 MB | 只剩環狀檔(已預先配置,不需要新空間)、極小的事件,以及一個小的狀態檔;樣本停止 |

**依狀況調整細節。** 觸發之後會每秒取樣一分鐘,但只在磁碟空間處於第一級時才這麼做。核心訊息暴增時,每分鐘最多記 120 行。

## 3. 卡住、很慢或斷電之後怎麼查

```bash
aio-sysmon last-crash
```

會顯示上一次是怎麼結束的。如果機器不是正常關機,它會印出判斷、最後一分鐘的數值、結束前的核心訊息,以及最後幾筆逐秒的紀錄,例如:

```
verdict:  the machine stopped without a clean shutdown; the input voltage fell in the last minute
last record before the stop: 2026-10-07 02:41:17
last minute: temp_max_c=52.0, load1_max=3.1, mem_avail_min_mb=11800, vin_min_mv=15200, vin_max_mv=19150, ...
```

可能的判斷依下列順序檢查:**輸入電壓下降**(電源供應、線材、電壓不足)、**過熱**、**記憶體耗盡**、**磁碟卡頓**、**結束前系統停頓**;如果都不是,就是「直到最後一筆紀錄數值都正常」,代表突然斷電、強制重置,或是沒有任何警告的卡死(這時應該去看核心訊息和快照)。被硬體看門狗(這台機器是 2 分鐘)重置的卡死,看起來也會是這樣。

如果是「很慢、但沒有卡死」:

```bash
aio-sysmon report --hours 3      # 逐小時摘要,加上重要事件
aio-sysmon events --kind anomaly # 什麼時候、為什麼被觸發
aio-sysmon snapshots             # 列出詳細快照
aio-sysmon snapshots stall       # 開啟名稱含 "stall" 的最新一份
```

快照回答的是*當下是誰在使用這台機器*:CPU 與記憶體前幾名的程序、卡在磁碟的工作、溫度、電源軌和核心訊息。

所有指令:

| 指令 | 顯示 |
|------|------|
| `aio-sysmon status` | 是否在執行、使用的空間、最新數值 |
| `aio-sysmon last-crash` | 上一次不正常結束的判斷,以及結束前的最後紀錄 |
| `aio-sysmon report [--hours N] [--since "YYYY-MM-DD HH:MM"]` | 逐小時摘要與重要事件 |
| `aio-sysmon ring [--rows N]` | 最新的逐秒紀錄(只有 root 能讀:請加 `sudo`;`last-crash` 用 `sudo` 執行時也會顯示) |
| `aio-sysmon events [--hours N] [--kind KIND]` | 事件(`anomaly`、`kernel`、`unclean_stop`、`tick_gap`、`clock_step`、`start`、`stop`) |
| `aio-sysmon snapshots [NAME]` | 列出快照,或印出其中一份 |

檔案都是純文字或 gzip,放在 `/var/log/aio-sysmon/`:`ring.bin`(固定大小的環狀檔)、`samples/`(每日 JSON 行)、`events.jsonl`、`snapshots/`、`last_known.json`、`run.json`。

## 3b. 機器吃緊時它怎麼保持運作

平常它只是一個安靜的一般程式(稍微優先:nice −5、不容易被 OOM 殺掉、記憶體固定在 RAM 裡,記憶體吃緊時不會被換出去,約 11 MB)。
只有觸發條件顯示機器**已經沒有回應**(`stall`、`iowait`、`disk_wait_tasks`、`memory_low`、`swapping`、`swap_high`、`hot`、`slow_disk_write`)時,
它才把自己暫時提高為低優先序的即時排程 60 秒,讓詳細取樣不被餓到,之後自動降回(事件 `priority`)。
只是忙(`load`、`cpu_saturated`)不會觸發。它不會暫停或影響其他程式。保險:優先序遠低於核心自己的執行緒;
監看執行緒在主迴圈停止前進時會降回一般;服務設有 `LimitRTTIME`,即時排程的程式連續運算 1 秒沒有睡眠,核心會直接終止它(systemd 再重啟)。
在這台機器上實測:服務的 15% CPU 上限**不會**限制即時排程(空轉迴圈用了 97%),所以升級期間靠上述保險;`LimitRTTIME` 在 1.1 秒後就殺掉了不睡眠的即時排程迴圈。`tools/sysmon_rt_test.sh` 可重複這些測試。如果機器卡到連紀錄器都跑不動,留下來的就是環狀檔與 `last-crash`。

## 4. 設定

`/opt/aio-dashboard/config/sysmon.yaml`(修改後執行 `sudo systemctl restart aio-sysmon`)。全部都是選填。最常用的項目:

| 設定 | 預設 | 說明 |
|------|------|------|
| `interval_s` | `5` | 每幾秒一筆完整樣本 |
| `ring_mb` | `4` | 逐秒環狀檔的大小(每 4 MB 約 2 小時) |
| `max_total_mb` | 推算 | 整個資料夾的硬上限 |
| `retention_days` | `30` | 壓縮後的每日檔保留幾天 |
| `min_free_mb`、`critical_free_mb` | 推算、`512` | 上述磁碟保護的各級門檻 |
| `burst_s`、`burst_interval_s` | `60`、`1` | 觸發後的詳細取樣 |
| `triggers` | `{}` | 覆蓋任何門檻,例如 `{iowait_pct: 15, temp_c: 80}` |
| `lock_memory` | `true` | 把紀錄器固定在 RAM |
| `escalate`、`escalate_s`、`escalate_priority` | `true`、`60`、`10` | 上述暫時提高優先序 |
| `kmsg` | `true` | 複製核心的警告與錯誤(需要 root) |

## 5. 它看不到什麼

- **每個程序的磁碟使用量。** 這個核心沒有提供。磁碟問題改由整顆磁碟的忙碌率、請求時間、紀錄器自己寫入磁碟所花的時間,以及卡在磁碟等待的工作來呈現。
- **斷電前最後幾秒。** 環狀檔每 5 秒才寫入磁碟,所以最多可能少 5 秒;樣本則是每次寫入都會同步。
- **數值正常的卡死。** 如果直到最後一筆紀錄數值都正常,核心也沒有記錄任何東西,判斷會老實地這樣說:這指向電源、硬體或核心的問題,紀錄器無法再細分。
- **時鐘問題。** 機器如果沒有電池供電的時鐘,或硬體時鐘存的是當地時間(`timedatectl` 顯示「RTC in local TZ: yes」),剛開機時時間可能是錯的,直到校準為止;這台 Orin NX 曾快了 8 小時。每筆紀錄也都帶有開機後經過的時間,時鐘跳變會記成 `clock_step`,而 `last-crash` 與 `events` 仍找得到時鐘超前時寫下的紀錄。`sudo timedatectl set-local-rtc 0` 會讓硬體時鐘改存 UTC。
- **發行包。** `tools/build_release.sh` 產生的編譯版發行包目前不含紀錄器,要從原始碼目錄安裝。

## 6. 安裝、權限與移除

這是選配功能,**預設不安裝**:執行 `sudo deploy/install.sh --user <使用者> --with-sysmon` 才會安裝(裝過之後,再執行安裝程式會自動更新它)。它也會讓系統 journal 保存在磁碟上(`/etc/systemd/journald.conf.d/aio-persistent.conf`,300 MB),這樣核心自己的日誌在重開機後也還在。

服務以 root 身分執行,是為了讀取核心訊息和卡住工作的堆疊,但有沙箱限制:系統對它是唯讀、看不到家目錄,只有 `/var/log/aio-sysmon` 可以寫入。快照裡有程序的命令列,所以只有 root 與 `adm` 群組可以讀。

`sudo deploy/uninstall.sh` 會移除服務,但**保留紀錄**(它們是證據)。要刪除請自己刪 `/var/log/aio-sysmon`。
