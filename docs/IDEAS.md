## 1. 維護頁預設關閉,需要時才打開

> **部分完成(2026-10-08):** 維護頁整站都需要密碼了(`aio-dashboard password`,`maintenance.lock: all`)。下面的「只綁本機、臨時開放、診斷包」還沒做,仍可作為出貨機的額外保護。

**為什麼:** 出貨給客戶的機器不應該讓人看到或操作維護頁(重啟服務、啟停 driver、切換 Live/Bag)。原本維護頁在 `0.0.0.0:8081`,沒有登入,只靠 IP 白名單,而且和使用者頁共用同一份白名單。但完全不裝,現場出問題時又很難修。

**建議做法(討論後選定的 C 方案):**
- **產品機預設:** 維護頁只綁 `127.0.0.1:8081`,網路上連不到。使用者頁 `8080` 不變。
- **工程師需要時,兩種方式:**
  - SSH 通道,不改任何設定:`ssh -L 8081:localhost:8081 <user>@<機器>`,再開 `http://localhost:8081`。
  - 臨時開放:`sudo aio-dashboard maint on --for 2h`,時間到自動關回。適合現場只有平板、沒辦法 SSH 的情況。
- **測試機:** 安裝時加 `--maint-open`,行為和現在一樣,永久開放、隨時可連。選擇存在機器上,重跑安裝程式會保留;要切換時用 `--maint-open` / `--maint-local`。
- **診斷包:** `aio-dashboard diag`,把日誌、設定、服務狀態、紀錄器報告打包成一個檔案。客戶沒辦法讓我們連進去時,請他執行並寄回來。

**取捨:**
- 不建議合成同一個 port。合在一起後只能靠登入區分權限;分兩個 port 可以用「綁在哪個介面」這種簡單可靠的方式控制。
- 如果需求是「程式碼不要出現在客戶機器上」,可以用 `tools/build_release.sh` 做不含維護頁的發行包,代價是現場維修要另外帶完整版。

**建議順序:** 綁定設定加 `--maint-open` / `--maint-local` → `maint on/off --for` → `diag` 診斷包。最小的第一步就是把預設綁定改成 `127.0.0.1`。

## 2. ROS 做成選配模組

**為什麼:** 有些目標機器(例如 i.MX8)可能沒有 ROS。把 ROS 切出去後,核心在沒有 ROS 的機器上也能完整運作,而且這一步不管之後換不換語言都需要。

**現況(2026-10-08 查過程式碼):** 真正 `import rclpy` 或 ROS 訊息型別的只有約 700 行,不到全部約 4100 行的六分之一:
- `collectors/ros2.py`:417 行,負責主題/節點監看與取樣。
- `media/tap.py`:197 行,相機/光達預覽解碼。
- `collectors/gnss_monitor.py`:81 行,GNSS 狀態。

`ros_guard.py`、`ros_mode.py`、`dso_watchdog.py`、`process_control.py` 名字有 ROS,但只做行程管理與環境變數,不依賴 ROS 函式庫。導航資料走 UDP(`nav/decoder.py`),完全不經過 ROS。

**要先處理的耦合點:**
- `state/health.py`:沒有 ROS 模組時要顯示「未啟用」,不能當成故障。
- `__main__.py`:ROS 收集器與隔離檢查改成「有安裝才載入」。
- 網頁:Maintenance 的 ROS 頁、Overview 的 GNSS 燈與感測器燈要能隱藏。
- GNSS 燈:目前依賴 `NavSatFix`。沒有 ROS 時可考慮改用導航 UDP 封包的旗標,但語意不完全相同,要另外定義。

**做法:** 照 README「Optional modules」的模式,做成獨立資料夾、`--with-ros` 安裝旗標、`enabled` 設定,在 `feature/optional-ros` 短期分支上開發。模組的骨架已經有了(`aio_system_dashboard/modules.py`,第一個模組是 2026-10-08 的 replay),ROS 模組可以照同樣方式接上。

## 3. C/C++ 原生版與跨裝置部署

**為什麼:** 目標裝置包含 Jetson Orin NX、AGX,以及較低階的 NXP i.MX8。作業系統常常不同,也常常沒有網路。Python 版本與 wheel 依賴在這些機器上不好處理,Yocto 的 i.MX8 甚至可能沒有 Python。

**已確定的方向:**
- **不用 Rust**(團隊不熟,風險太高),原生版用 C++(C++17,寫簡單一點,用 sanitizer 測試)。
- **Python 與 C++ 並行可以,但要有規則:**
  - 以 Python 為標準版,C++ 只移植選定模組。
  - 以「介面」為界:前端共用,後端提供相同的 HTTP JSON;紀錄器共用檔案格式。
  - 用同一組一致性測試確保兩邊輸出相同。
  - 新功能先在 Python 做完,穩了再決定是否移植。
- **arm64 執行檔不是自動通用。** glibc、libstdc++ 版本、musl 都會造成問題。要用**靜態連結**,或在**最舊的目標系統**上編譯。

**建議順序:**
1. 用 `tools/target_survey.sh` 在 AGX 與 i.MX8 各跑一次,收集 glibc、作業系統、Python、ROS、systemd、可用感測節點。這台 Orin NX 的結果:Ubuntu 22.04、glibc 2.35、GLIBCXX 3.4.30、有 `libc.a`、gcc 11、ROS Humble 有 `rclcpp`。
2. 先做第 2 項(ROS 選配)。
3. 紀錄器的 C++ 版:只讀 `/proc`、`/sys`,靜態連結成單一小執行檔,沿用現有檔案格式,用 Python 版的測試當標準。缺少的資料(例如 i.MX8 沒有 INA3221)要降級而不是出錯。
4. 儀表板核心(不含 ROS)用 PyInstaller 或 Nuitka 打成單一執行檔,驗證依賴問題是否解決。
5. 視情況再把 ROS 模組改成 `rclcpp`。它是最吃 CPU 的部分,原生化效益最大。

**不建議:** 整套儀表板重寫。網頁後端、行程控制、各種防呆都要重做,而且目前還在密集調整,Python 改完就能跑的彈性很重要。

## 5. 效能與負載的小改善

來自 2026-10-06 的全面檢查,當時列為「可以再做」:

- **使用者頁輪詢從每秒 5 次降到 2 次。** 目前 `product.js` 每 200 ms 抓一次 `/api/state`。無頭瀏覽器開著頁面就吃約 18% 單核心,實際有 GPU 合成會更多。在這台機器上開網頁加遠端桌面時特別明顯。
- **DSO 記憶體上限:已完成(2026-10-08)。** DSO 曾以每秒 25 MB(等於相機原始影像串流)持續增加,把 RAM 與 swap 用完,整台機器卡死。監控現在會在 DSO 超過 `dso_watchdog.max_memory_mb` 時重啟它。**根本原因要 DSO 修:** ROS wrapper 似乎無上限地排隊相機影像,應該在處理不及時丟掉舊影像。
- **記憶體用完時讓系統更快恢復。** 16 GB 的 swap 放在 NVMe 上,記憶體用完時機器會卡好幾分鐘,而不是直接殺掉失控的程式。可考慮縮小 swap,或裝 `earlyoom` 之類的工具,在記憶體快用完時直接結束最大的程式。DSO 的上限已涵蓋這次的情況,這是對其他程式的額外保護。
- **硬體時鐘改存 UTC。** 這台的 RTC 存的是當地時間,開機後到校時前時間快 8 小時,早期的紀錄時間都會錯。`sudo timedatectl set-local-rtc 0` 即可修正。
- **DSO 崩潰重試加退避。** 目前每 30 秒重試一次(`dso_watchdog.retry_s`)。相機畫面沒有紋理時 DSO 會一直崩潰,每次載入約 180 MB 的程式,產生大量吵雜紀錄。可改成連續失敗後逐步拉長,例如到 5 分鐘。
- **相機網路改用巨型封包(jumbo frame)。** GigE 相機約 26 MB/s、每秒約 1.3 萬次中斷,目前 MTU 1500。改 MTU 要相機與網卡兩邊都設定。
- **磁碟空間。** AIO NAV 每小時寫約 270 MB 的輸出,長時間運行要有清理或輪替策略。

## 7. AIO NAV 本身的配合

這些要改 AIO NAV,不是改儀表板:

- **多送一份 UDP 到本機另一個埠**(例如 `127.0.0.1:9001`)。`output_udp` 只能設一個目標,目前給了外部電腦 `192.168.116.154:9000`。本機 `127.0.0.1:9000` 只能有一個程式綁定,誰先綁誰收得到。現在 `aio-nav-ui` 已經不用,所以暫時沒有衝突;如果之後又需要另一個本機程式讀資料,就需要這個功能。
