# 方向(草稿,討論中)

先定方向,再整理功能,最後才改程式。這份文件記錄已經決定的和還沒決定的。功能清單與彼此的關係見 [FEATURES.md](FEATURES.md)。

最後更新:2026-11-17

## 1. 這個程式是什麼

**核心需求:監控。** 一個程式看著我們的軟體(AIO NAV 等)跑得怎麼樣,以及各個零件(IMU、GNSS、相機、網路、電腦本身)有沒有問題。這部分目前基本上都做到了。

**進一步的需求:找出原因,接著檢修。** 從監控看到的現象,追到原因,再在同一個地方處理。

**額外的需求(不是主軸):**
- 出貨機無人值守,自我檢查、全自動。
- 輸出給車輛(0x05 狀態封包)。這部分之後可能拔出來,在其他專案做成獨立功能。

## 2. 功能分層(草案)

依照上面的優先順序分層。下層不依賴上層:拿掉上層,下層照常運作。

| 層 | 目的 | 目前屬於這層的功能 |
|----|------|--------------------|
| **1. 監控**(核心) | 看到現在怎麼樣 | 0x04 接收解碼與 AIO NAV 狀態、系統 / 服務 / ROS / 網路、感測器燈號(IMU、GNSS、相機、LiDAR)、事件紀錄、系統紀錄器(sysmon)、GNSS 校時 |
| **2. 診斷** | 找出原因 | 診斷頁、GNSS / RTK 頁、即時預覽、ROS 主題、事件、sysmon 的 last-crash、紀錄檔下載、終端機 |
| **3. 檢修與設定** | 處理問題、調整 | 啟停 AIO NAV / drivers、AIO NAV 設定編輯器、槓桿臂、靜止偵測校正、Wi-Fi / 熱點、密碼 |
| **4. 自動運行**(選用) | 沒有人時自己處理 | 自動啟動、DSO / driver 監控、ROS 隔離檢查 |
| **5. 對車輛輸出**(選用,將來可能獨立) | 告訴車輛能不能用 | 0x05、給車輛的 10 種 readiness 狀態與 inhibit bits、「READY 需要 RTK」、vehicle gate、熱點封包複本 |
| **資料** | 收集與重播 | 資料下載、Bag 重播(目前閒置,方向待定) |

**目前和分層衝突的地方:**
- 健康評估(第 1 層)和給車輛的 readiness(第 5 層)交織在 `state/health.py` 裡。自動啟動(第 4 層)也讀 readiness。要把輸出拔出去,得先把這兩者分開。
- 「READY 需要 RTK」預設開,把第 5 層的規則套到整台機器上。但 RTK 其實要依環境決定(見第 3 節)。
- 使用者頁以「Ready / 對準進度」為主,是車輛操作員的視角。但出貨機平常沒人操作,第 1–3 層的使用者是工程師和第一次設定的人。

## 3. 已確定的事

**三種機器:**

| 機器 | 用途 | 操作的人 |
|------|------|----------|
| 出貨機 | 接車輛,無人值守,自我檢查、全自動 | 沒有人;出問題時工程師到現場 |
| 測試機 | 監控整機狀態、測試各種東西 | 工程師 |
| 開發機 | 遠端修問題時用來模擬的環境 | 工程師 |

**順序:** 先把所有功能整理好、修好,再依照情境決定每種機器要裝哪些選配。

**各功能當初的需求:**

| 功能 | 需求 | 結論 |
|------|------|------|
| 熱點 | 裝置大多在沒有網路的地方。第一次使用時,用手機或平板快速連進裝置做設定和操作 | 屬於「第一次設定」。沒有網路的環境本來就沒有 NTRIP,所以和 Wi-Fi 上網的衝突不是問題 |
| RTK | 不是一定要有,依環境決定。沒有 RTK 時,有些偵測和判斷要跟著改變 | 不應該預設強制。由環境設定決定 |
| 網路從哪來 | Wi-Fi 或網路線,依裝置而定 | 和熱點、RTK 相關,是環境設定的一部分 |
| 槓桿臂(Setup) | 讓使用的人依照自己的載具調整安裝位置,軟體才能正確運作 | 使用者自己的設定,保留在使用者頁 |
| Bag 重播 | 當初為了測試做的,目前閒置。方向應該是:收資料,之後可以重播 | 待定(有想法,另外整理) |
| 桌面 App(aio-nav-ui) | 已經沒有了 | 相容的部分可以移除;UDP 9000 不再有搶埠的問題 |
| 0x05 輸出 | 當初案子趕工,需要輸出給車輛 | 第 5 層,將來可能獨立 |

**第一次設定:** 要有這個步驟(例如透過熱點連進去),決定這台裝置的環境:網路從哪來(Wi-Fi / 網路線 / 沒有)、有沒有 RTK、有沒有接車輛。之後各功能依照這些設定運作,不再各自猜。

**使用者頁(8080)的對象:** 很廣泛,是一般性的頁面。例如採數據的人(研發之外的人)要能做基本的判斷:系統正常嗎、資料能用嗎、不能用的話找誰。真的要做事還是去維護頁。

**看與改分開:** 大部分資訊都可以開放出來看,由使用者自己決定要不要看;**會影響運作的操作留在維護頁**。

**環境常常切換:** 同一台裝置常在有網路 / 沒網路、有 RTK / 沒 RTK 的地方之間移動。所以環境不能是「設定一次就固定」。

**沒有 RTK 時:** 主要影響 EKF 的收斂。誤差比較大,所以對準和收斂都需要更多時間,過程也不一樣。對儀表板的意思是:時間限制、進度提示和「多久算異常」都要依 RTK 設定調整,不能用有 RTK 時的標準判斷。

## 3a. 設計原則(草案)

**原則一:看是開放的,改才分等級。** 依照操作的影響分三級:

| 等級 | 例子 | 在哪裡、要什麼 |
|------|------|----------------|
| 看 | 所有狀態、燈號、診斷資訊、GNSS 細節、事件、紀錄檔下載 | 都可以看,不用密碼。使用者頁顯示重點,細節頁也開放唯讀 |
| 改自己的設定(可以復原,不會中斷導航) | 語言、槓桿臂、Wi-Fi、現在的環境 | 使用者頁可以改,有確認與事件紀錄 |
| 影響運作 | 啟動 / 停止、重啟 drivers、AIO NAV 設定編輯、熱點、靜止偵測校正、終端機 | 維護頁,要密碼 |

現在的程式已經有一半是這樣:`maintenance.lock: tools` 就是「看免密碼、改才要密碼」。差別在於預設是 `all`(整個維護頁都要密碼),以及使用者頁的啟停按鈕不用密碼。

**原則二:環境先自動偵測,使用者可以改。** 環境常常切換,所以不能靠每次手動設定。大部分可以偵測:

| 環境 | 怎麼偵測 | 現在有沒有 |
|------|----------|------------|
| 有沒有網路、走哪條 | 連外測試、預設路由的介面 | 有(Internet 燈、路由) |
| 有沒有 RTK 修正 | 接收機的 NTRIP 狀態、定位品質 | 有(GNSS / RTK 頁、GNSS 燈) |
| 有沒有接車輛 | 不容易自動偵測(UDP 沒有回應) | 沒有;需要人設定 |

頁面上顯示「現在的環境」和它是怎麼判斷的;判斷錯時使用者可以覆寫。

## 4. 討論中

- **測試機和開發機的分界。** 草案:用「資料從哪來」區分(測試機:真的感測器;開發機:Bag 重播或模擬)。
- **採數據的人要看到什麼。** 見第 3a、5 節的草案。
- **使用者頁的啟停按鈕。** 照原則一屬於「影響運作」,應該移到維護頁;但採數據的人可能需要自己啟停。待決定。
- **給車輛的訊號。** 不是正常運行時,繼續送 MAINTENANCE 還是不送?需要和車輛端確認。等第 5 層拔出去時一起決定。
- **沒有 RTK 時的具體差異。** 哪些時間限制和判斷要改,需要和懂 EKF 的人一起列出來。

## 5. 整理計畫(草案)

依照上面的方向,現有功能大致這樣處理:

| 項目 | 現在 | 改成 |
|------|------|------|
| 環境設定 | 散在各處:`readiness.require_rtk`、`wifi.*`、`status_udp`、出貨 yaml | 新增「第一次設定」:網路來源、RTK 有無、有沒有接車輛。其他設定從這裡推導 |
| READY 需要 RTK | 預設開,屬於整台機器 | 由環境設定的「有沒有 RTK」決定;沒有 RTK 時改用較寬的時間限制與判斷 |
| 使用者頁 | 車輛操作員視角:Ready、對準進度、啟停 | 採數據的人的視角:系統正常嗎、資料能不能用、要做什麼。保留啟停、槓桿臂、Wi-Fi |
| 給車輛的 readiness 與 0x05 | 和健康評估寫在一起,自動啟動也讀它 | 拆成獨立的一層:核心只產生健康狀態,車輛輸出讀核心,核心不讀它 |
| 自動啟動 | 讀給車輛的 readiness | 改讀核心的健康狀態;有沒有接車輛只影響「READY 後重啟要等靜止」這類規則 |
| Bag 重播 | 選配,和其他功能沒有協調 | 暫時維持;等「收資料再重播」的方向定了再改。至少讓它在重播時不送 0x05、不餵時鐘 |
| 桌面 App 相容 | 程式註解與文件仍有提到 | 移除說明;保留「儀表板重啟時接手已在跑的 AIO NAV」 |
| 熱點 | 維護頁的選配 | 列為「第一次設定」的入口之一 |
